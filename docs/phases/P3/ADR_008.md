# ADR-008 — P3-F: Actor-aware collector adapter (Master criterion amendment)

**Status:** APPROVED by user (selected option B on 2026-10-22)
**Supersedes:** the P3-A assumption that `AsyncBatchedCollector` could drive a staged conditional policy
**Relates to:** `PA4-P3-DESIGN-v1.0` §1.3 (P3-F fallback), §6 (G3-A)

---

## 1. Decision

P3 implements an **actor-aware collector adapter** (`pa4/collector/`) that owns the
staged two-seat acting loop and drives the existing P2 `PA4EnvBase` through the
real P1 `InferenceServer` + `ProcessSlotTransport`.

The TorchRL `AsyncBatchedCollector` is **not** used as the outer collector for this
phase. The master architecture requirement "collector uses TorchRL
`AsyncBatchedCollector`" is amended, for P3 only, to:

> "The collector must use real TorchRL inference-service components
> (`InferenceServer` + `ProcessSlotTransport`) for central policy evaluation, emit
> standard TensorDict transitions, and satisfy the bounded/backpressure/lifecycle
> requirements of the phase. The outer orchestration loop may be a narrow,
> documented adapter when the environment's acting protocol is incompatible with
> the stock collector."

This amendment does **not** lower any correctness, privacy, legality, provenance,
accounting or lifecycle requirement. It changes only which object performs outer
orchestration.

## 2. Why the stock collector cannot be used

### 2.1 Acting-contract mismatch (the fundamental reason)

`torchrl 0.14.1` `AsyncBatchedCollector` (`_async_batched.py`, sha256
`bf5ba4b31e4be0c71adc569bd3fa3db5ce6704ccdd81edfe1ef478f35be47c96`) acts as:

```python
policy_output = client(observation)                     # one exchange
action_td = observation.update(policy_output)
transition, observation = env.step_and_maybe_reset(action_td)
```

The client is `transport.client()` or a user callable. It receives **only a
TensorDict**, holds no reference to the environment, and `PolicyClientModule` is
documented as a *remote* client with "no lifecycle rights".

A P2 action packet instead requires, per requesting seat, one `ENCODE` plus one
`STEP` per prefix level (up to 4) plus a `RESET`, where each `STEP` needs the Rust
engine's candidate table **for the current prefix**. That candidate table is only
obtainable from the live `NativeEngine` inside the worker. The stock collector
provides no point at which the policy can query it.

**Conclusion: the incompatibility is architectural, not incidental.** No amount of
policy-side adaptation closes it, because the missing object is the native engine,
not the policy.

### 2.2 The observed shape error (diagnosed in full)

The collector fails even before reaching the policy, with:

```
Received a new batch size torch.Size([1, 1]) with an existing
batch_size torch.Size([1]) in a lazy TD.
```

Root cause, `torchrl/envs/async_envs.py:574` in `_maybe_make_tensordict`:

```python
if tensordict.shape != (1, *self.env_batch_sizes[env_idx]):
    tensordict = tensordict.unsqueeze(0)
```

- P2's merged tensor is already environment-batched: `shape == (1,)`.
- `env_batch_sizes[0]` is `torch.Size([1])`, so the comparison target is `(1, 1)`.
- `(1,) != (1, 1)` is true, so an **extra** leading dimension is added → `(1, 1)`.
- P2 then correctly rejects it:
  `Expected a tensordict with shape==env.batch_size, got torch.Size([1, 1]) and torch.Size([1])`.

Verification (measured, not inferred):

| Step | Observed |
|---|---|
| P2 reset observation shape | `(1,)` |
| action packet shape | `(1,)` |
| `obs.update(packet)` shape | `(1,)` |
| collector comparison target | `(1, 1)` |
| unsqueeze triggered | **yes** |
| resulting shape | `(1, 1)` |
| `env.step((1,1))` | rejected, as designed |

Direct `env.step_and_maybe_reset(merged)` **succeeds** with shape `(1,)`, which
proves P2 is correct and the extra dimension originates in the collector's pool
plumbing. `stack` mode is not user-configurable, so this cannot be worked around
from PA4 without patching TorchRL.

Note this is a *separate* defect from §2.1. Even if it were fixed upstream, the
acting-contract mismatch in §2.1 would remain, so fixing it would not unlock the
stock collector for PA4.

## 3. What P3-F keeps from TorchRL

- `torchrl.modules.inference_server.InferenceServer` (process backend)
- `torchrl.modules.inference_server.ProcessSlotTransport` (fixed slot layout)
- `tensordict.TensorDict` transitions with the exact P2 schema
- `check_env_specs` on the P2 `PA4EnvBase`

## 4. What P3-F replaces

Only the outer orchestration loop: bounded worker processes, bounded transition
queue, staged acting, deterministic shutdown. It never:
- computes game rules,
- chooses legality,
- re-implements `env.step`,
- or replaces the native engine.

## 5. Explicit non-weakening statement

This ADR changes **which object orchestrates**. It does not change:

- the five G3 gates or their PASS criteria,
- the requirement for a real instrumented CUDA forward with B ≥ 2,
- the requirement for ≥ 16 unique natural completions from ≥ 2 workers,
- the identity, privacy, provenance or fail-closed requirements,
- the "no illegal actions / no duplicate completions" requirement.

If P3-F cannot satisfy a gate, that gate is reported failed — the amendment is not
a licence to relax it.
